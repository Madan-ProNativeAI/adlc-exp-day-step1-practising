**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Assuming the feature is implemented within the required layout, the primary touchpoints are `src/backend/Program.cs` for startup, dependency injection, environment-variable binding, ARM/data-plane Cosmos initialization, and HTTP client registration; `src/backend/Models/` for conversion request/response and audit entities; `src/backend/Services/` for exchange-rate retrieval, response-shape normalization, and audit persistence; `src/backend/Repositories/` for Cosmos DB CRUD access; `src/backend/Controllers/` or `src/backend/Endpoints/` for conversion and audit retrieval APIs; `src/backend/Tests/` for backend behavior verification; `src/frontend/index.html` for the `__VITE_API_URL__` placeholder; `src/frontend/src/` for the conversion form, result display, and audit lookup UI; and the frontend container entrypoint script under `src/frontend/` for runtime `VITE_API_URL` replacement.

**In Scope:**
- Add a backend API in `src/backend` that accepts a currency conversion request with source currency, target currency, and amount.
- Call the external rate provider using a base URL sourced from `CURRENCY_API_BASE_URL`, normalize provider responses through an internal abstraction, and compute a converted amount.
- Persist one audit record per successful conversion in Cosmos DB, including request values, resolved rate, converted amount, provider date/sequence markers if present, and the exact backend-generated execution timestamp with sub-second precision.
- Add a backend API in `src/backend` to retrieve a prior conversion audit record by identifier for auditor lookup.
- Return domain-safe error responses for upstream HTTP, timeout, and deserialization failures without leaking raw exception details.
- Add frontend behavior in `src/frontend/src/` that lets a user enter an amount and currency pair, submit the conversion request, see the converted amount immediately, and fetch a prior audit record by its identifier.
- Preserve runtime frontend API URL injection via `__VITE_API_URL__` replacement in `src/frontend/index.html` and the container entrypoint script.
- Add automated tests covering conversion success, audit persistence/retrieval, provider-schema normalization, and graceful upstream failure handling.

**Out of Scope:**
- Historical trend charts, batch conversion uploads, or scheduled background rate sync.
- Editing or deleting audit records after they are written.
- User authentication, authorization, or role-management changes beyond existing application behavior.
- Export formats such as PDF, CSV, or spreadsheet generation for auditors.
- Rate caching layers, retry dashboards, circuit-breaker telemetry screens, or other operational enhancements not required to satisfy the core conversion-and-audit workflow.
- Provisioning new Azure infrastructure beyond the application startup behavior already required by the Known Constraints.

**Feature Constraints:**
- Use `IHttpClientFactory` in `src/backend/Program.cs` and the rate-provider service instead of creating raw `HttpClient` instances directly.
- Represent monetary inputs, exchange rates, and converted amounts as `decimal`, never `double` or `float`.
- Generate the authoritative audit execution timestamp on the backend in UTC and persist it in round-trip ISO 8601 format or an equivalent lossless representation that preserves fractional seconds.
- Do not trust any client-supplied timestamp for compliance fields; the frontend may display timestamps but must not author them.
- Isolate external provider parsing behind a dedicated mapper/service so backend API contracts and Cosmos audit documents do not depend on provider field names like `rates` or `conversion_rates`.
- Return RFC 7807 `ProblemDetails`-style responses for non-success cases, with a stable domain error for rate-provider unavailability.
- Keep audit records append-only: once a conversion record is created, retrieval is read-only.
- Include the persisted audit record identifier in the successful conversion response so the frontend can present an auditor reference immediately.

**Expected Outcome:** A user can submit a request such as `{ "fromCurrency": "USD", "toCurrency": "EUR", "amount": 100.00 }` from `src/frontend`, and the backend returns a success payload containing the original amount, a resolved exchange rate, a converted amount, an audit record identifier, the provider's effective date marker if available, and a backend-generated execution timestamp with fractional seconds. For example, if the provider returns an effective rate of `0.9234`, the API response should contain a converted amount of `92.34` and an audit reference that can be used immediately in a follow-up retrieval request. A subsequent fetch by that identifier returns the same persisted values needed for audit reconstruction, including source currency, target currency, original amount, rate, converted amount, provider marker, and backend execution timestamp. If the upstream provider is unavailable or returns an unusable payload, the backend responds with a domain-safe `ProblemDetails` response with HTTP 503 rather than exposing raw network or JSON parsing exceptions, and no false-success audit record is written.
